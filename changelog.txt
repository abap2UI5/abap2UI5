==================

Legend
------

unreleased
----------
! the startup page was rebuilt. It reads top to bottom: the five quickstart
  steps, then one row per sample repository - icon, repository name and what
  is in it, the description word for word the one the repository carries on
  GitHub - where the name opens that repository's overview app when it is
  installed on this system, and GitHub when it is not, in a new tab either
  way, with a "not installed" status behind the name of the rows that are
  not. A Documentation section follows, carrying the repository and the docs,
  which is where the "Keep learning" section went. The page's footer carries
  one line of icons: issues, pull requests, the Slack channel and sponsoring,
  and at its right end the system information, which stays a popup - it
  answers a question that is asked once. The draft entries there are given as own/total
  now (z2ui5_cl_core_srv_draft=>count_entries_total( )), the figure that says
  whether the cleanup is keeping up on this system. The title row is icons
  only: the documentation, the repository (globe) and, where the class
  exists, the configuration
- BREAKING: removed render_documentation( ), render_system_popup( ) and
  render_contribution( ) from the public section of z2ui5_cl_app_startup,
  together with cs_event-open_info, cs_event-close and cs_event-open_debug.
  The "Keep learning" section they rendered is gone, the system popup is
  built by a private method now, the Join in section became a line of icons,
  and open_debug was a header button that only said which key opens the
  developer tools - that button is gone too. The class is the framework's own
  start page - its render_* methods are the page's own internals, not
  something an app calls - but they sit in src/02, so the removals are
  recorded here and in the API snapshot. Everything that replaced them is
  private, including the two event names the page now uses: a page internal
  does not belong in the public contract
! check_sticky and check_initialized moved off z2ui5_if_app into the
  framework's own app wrapper (z2ui5_cl_core_app=>mv_check_sticky /
  mv_check_initialized), where mv_nav_mode and ms_session already live. They
  are framework bookkeeping, not something an app implements, and every
  reader already held that wrapper - the http handler even reached through
  it to CAST the app back out. Both interface attributes stay and are kept in
  sync by z2ui5_cl_core_app=>app_compat_mirror( ), so an app that READS them
  still sees the truth; a direct WRITE is no longer honored -
  client->set_session_stateful( ) switches sticky on and
  client->check_on_init( ) answers the lifecycle question. id_draft and
  id_app stay on the interface and are NOT obsolete: id_draft is the handle
  db_load_by_app( ) resolves an app reference by, and both are needed at
  moments when no wrapper exists yet - the interface now says so at the
  declaration
- BREAKING: removed cs_event-nav_to_route from z2ui5_if_client, together with
  its frontend handler and Router.navToApp( ). It navigated to another app by
  writing the hash and letting the router's hashChanged handler start the
  target - a second, frontend-side way into a navigation the backend already
  owns. Use nav_app_call( ) instead: it is the real navigation (the target app
  is instantiated on the server, the calling app is preserved on the stack),
  and with routing switched on (follow_up_action( cs_event-set_nav_routing ))
  it pushes the very same route history entry, so Back keeps working exactly
  as before. No sample or framework app used the event
- BREAKING: removed cs_event-history_back from z2ui5_if_client, together with
  its frontend handler. It was a one-line wrapper around history.back( ) from
  the era before follow_up_action( ) took raw JavaScript: pass the expression
  directly - follow_up_action( |history.back()| ) - or, for navigation inside
  the app, use nav_app_leave( ), which returns to the calling app through the
  app stack instead of stepping the browser history. The only caller in the
  ecosystem was an experimental sample, removed alongside
! cs_event-wizard_set_next_step is obsolete, and the interface says so. It
  bundles the two calls a UI5 controller makes on a Wizard
  (discardProgress( oStep ) + oStep.setNextStep( oNext )) into one fixed pair;
  both are on the CONTROL_METHODS whitelist, so the same flow is two
  follow_up_action( cs_event-control_by_id ) calls - which additionally reach
  goToStep, a step the bundled event cannot express. The constant and its
  handler stay and keep working
! custom_mapper / custom_filter of _bind( ) are obsolete, and the interface
  says so. Both hand an app a reference into the bundled AJSON library
  (src/00/01), a mirrored copy of an external project rather than a contract
  this framework owns. The declarative parameters cover what they were
  reached for - omit_initial / omit_initial_paths for initial fields, json for
  a JSON node - and anything else is better shaped in ABAP before binding.
  Both are still evaluated and keep working; zero usages across samples,
  samples-controls and samples-stack
* the developer tools kept showing the POPUP/POPOVER tabs of a dialog an app
  had closed in the browser without a roundtrip
  (follow_up_action( cs_event-popup_close / popover_close )). Both close
  paths always ran the same code - the backend formats either close as the
  ["VIEW_SLOTS","destroy","<slot>"] action that popup_destroy( ) queues, and
  it lands in ViewSlots.destroy either way - but the developer tools did not
  read the slot: they scraped the last response for the display action that
  had opened it, and a roundtrip-free close leaves that response current.
  ViewSlots now records the XML a slot was filled with next to the live
  instance (setView) and drops it in destroy( ), so the tools read the slot
  itself for all five slots and both close paths look the same
! _event_client( ) is obsolete - follow_up_action( ) is the same call in the
  same position now, and the interface says so. Since follow_up_action( ) has
  a RETURNING parameter, a call whose result is CONSUMED (the view-attribute
  form v = client->follow_up_action( val = ... t_arg = ... )) takes its
  IF result IS SUPPLIED branch straight to get_event_client( ) - the entire
  body of _event_client( ), so the roundtrip-free wire it emits is identical.
  One method both schedules a frontend action and wires one; the second name
  was half of it. The one difference is follow_up_action( )'s leading CASE,
  which claims cs_event-set_nav_routing / set_push_state /
  set_app_state_active before that branch - those three are backend-side
  navigation options rather than frontend handlers, so wiring one into a view
  attribute never dispatched anything under either name. _event_client( )
  stays in the public API and keeps working; the framework's own startup app
  was renamed, the frozen src/99 image-editor popup keeps its call. The
  abap2UI5-linter reports the leftovers as obsolete-frontend-event and
  rewrites them with --fix
! small performance cleanups in the rendering/serialization hot paths, no
  behavior change: both view builders concatenate child elements through a
  string table instead of re-copying the accumulated XML per sibling,
  z2ui5_cl_ai_xml=>xml_escape no longer builds its escape table on every
  attribute (chained replaces, same as z2ui5_cl_ui5_view_builder), and the
  event serializer runs its positional-placeholder regex only for arguments
  that start with a brace instead of on every argument
! z2ui5_cl_ui5_view_builder=>new( ) is now factory( ) - the same name the
  predecessor z2ui5_cl_ai_xml uses, so both builders start a view the same
  way and the method no longer shares its name with the NEW operator
! z2ui5_cl_ui5_view_builder sets every attribute through att( ), and att( )
  now lands on the element it FOLLOWS: the child just added by ele( ) or
  tag( ), or the node itself while it has no children yet. tag( ) is
  therefore the form for any leaf, whatever its attributes are - it used to
  be that an att( ) after a tag( ) attached to the parent, so a leaf could
  carry literals only, and only through the t_att table. That table is gone,
  with it the public type ty_t_attr that existed to type it and the
  protected parse_attr( ) that split its `key=value` strings on the first
  `=`; a bind or an event now works on a tag( ) like any other value. What
  the rule costs is its flip side: once an element has a child, att( ) can
  no longer reach it, so an element gets its attributes before its first
  child - the test that pinned the opposite (att_after_children) is gone
  with the behavior. The two removals are recorded in the API snapshot; the
  class was added after v1.142.0 and has never been part of a release, so no
  downstream app can hold a =>new( ) or a t_att call
+ the src/99 test classes are back and run in CI: all 27 deleted
  testclasses (util, pop, cx) are restored, the two disabled xml_view
  suites are re-enabled, and the pop tests assert against the
  t_action_front rows that replaced the removed s_set slot structs (the
  per-slot check_update_model flag has no successor - the model push is
  automatic); npm run unit no longer excludes src/99, three tests that
  need real-system facilities (second-exact timestamps, REPOSRC) are
  skipped in the NodeJS runtime like the existing AJSON skips; the src/99
  freeze now covers the production code only - *.testclasses.abap and the
  .clas.xml sidecars are exempt in both the check_frozen_paths workflow
  and npm run check:frozen, so the tests can follow the core internals
  they assert on
* a pending backend timer (START_TIMER) no longer fires its event into a
  destroyed controller - an FLP close or re-launch left the timeout armed
  and it would post the old app's event against the new session
! an app switch tears POPUP/POPOVER down implicitly - the response names
  its app, so the frontend destroys the standalone slots whenever the
  class changes and the two destroy actions no longer travel with every
  navigation (a hop to another instance of the SAME class still queues
  them backend-side); the leaving app's explicit destroys now survive the
  hop, so a view_destroy( ) before nav_app_call takes effect even when
  the called app renders no MAIN view of its own
! a plain nav_app_call sends no ROUTER action - the route-push intent
  only travels when hash routing is active for the target app
* the MessageToast Dock warning is really gone now: sap/m/MessageToast
  captures the Popup.Dock DataType in a module closure at load time, and
  sibling define-dependencies carry no execution-order guarantee - on
  loaders that ran the toast factory before Popup's, the captured type
  stayed broken for the whole session and every toast (even with valid
  positions, e.g. the MessageToast configurator sample) logged
  '"center bottom" is not of type "sap.ui.core.Popup.Dock"'. The control
  is now required lazily AFTER Popup is guaranteed loaded, so the capture
  always works
* a popover opened in the SAME roundtrip that builds its anchor view
  waits for the anchor to render before openBy - and loading
  sap/ui/core/Popup eagerly registers the Popup.Dock enum, which stops
  MessageToast from logging '"center bottom" is not of type
  "sap.ui.core.Popup.Dock"' for its own default position
- the developer tools dropped the NEST/NEST2 model tabs - nested views
  inherit the MAIN view's model by propagation, it was the same data
  shown twice
- the developer tools dropped the System tab - everything it showed lives
  in the remaining tabs or the exported state
! developer-tools tabs grey out when they have nothing to show (no log
  lines, no model data for the slot) instead of opening on an empty view
* an app switch clears the previous app's keyboard shortcuts - they no
  longer fire the old app's event names into the new one
! framework actions travel without the CONTROL_GLOBAL dispatch prefix -
  internal only: a backend-built action is ["VIEW_SLOTS","display",...],
  and the frontend dispatches every whitelisted global target by its own
  name (the prefixed eF( ) form stays accepted for apps and skew)
! the wire sheds its derivable bytes - internal only: a MODEL key in the
  response IS the model push (no updateModel action travels; the frontend
  pushes into every open slot when a model arrived), the routing mode is
  only re-sent when the frontend may not hold it (app start, navigation
  hop, mode change - not on every event roundtrip), and the live device
  fields (orientation/resize) travel only when they changed since the
  last send, stored with the draft like the rest of the device block
! the wire got leaner again - internal only: a display action implies the
  slot's teardown (the frontend destroys implicitly, no destroy action
  travels before a display), the ROUTER/sync action only travels when the
  roundtrip carries nav intent (the frontend syncs the URL once per
  response on its own, with the response id), and a request omits an empty
  HASH field
* a roundtrip that re-displays a NESTED view without its MAIN view pushes
  the model too - the nested view inherits the MAIN model by UI5
  propagation and bound against the previous roundtrip's data (broke the
  three-column FlexibleColumnLayout samples 098/104)
* the default Content-Security-Policy no longer names frame-ancestors in
  the <meta> tag - browsers ignore the directive there and warned on every
  page load; cross-origin framing stays forbidden via the
  X-Frame-Options: SAMEORIGIN response header
+ the http handler asks the ICF runtime to gzip its responses
  (if_http_response set_compression) when the client accepts it - the GET
  shell carries the whole embedded frontend and every POST roundtrip the
  model JSON, so this cuts 70-85% off the transfer on installations whose
  ICM profile does not compress already, and is a no-op on ones that do
  (and on the cloud stack, where the platform router owns compression)
- BREAKING: removed set_nav_back( ) and set_nav_routing( ) from
  z2ui5_if_client. Both are follow_up_action events now: history back rode
  cs_event-history_back (itself removed later in this release, see above),
  routing is configured with
  follow_up_action( val = cs_event-set_nav_routing t_arg = ( mode ) ) - the
  new constants set_nav_routing, set_push_state and set_app_state_active sit
  in cs_event with full documentation. set_push_state( ) and
  set_app_state_active( ) stay as methods and delegate to the events
! message_toast_display( ) / message_box_display( ) queue follow-up actions
  now: several calls in one roundtrip all show (the last call no longer
  silently wins), they appear in call order together with the app's other
  follow-up actions, and they run after the view rendered instead of before
  the response was processed
! the response wire got leaner - internal only, no app-facing change: the
  action lists travel as real nested JSON arrays instead of escaped strings,
  an unchanged model sends no MODEL key at all, and the session-constant
  browser data (UI5 build, device profile, ComponentData, page location)
  travels once per page load instead of with every roundtrip, stored with
  the draft and merged back for client->get( )
! the frontend internals were restructured - internal only: the action
  handlers live in core/actions/ domain modules behind the FrontendAction
  registry, the slot display machinery in core/actions/Slots.js, the
  session block in core/Session.js and the focus/scroll capture in
  core/ScrollFocus.js; the backend serialization moved into
  z2ui5_cl_core_action_front, the class that owns the frontend queues
! the model is now pushed AUTOMATICALLY when an event round-trip changed it,
  and the manual push methods are obsolete. The framework compares the model
  state before main( ) - taken after the incoming two-way deltas were applied,
  so what the client already knows never triggers a push - with the state
  after main( ) returned, and when they differ sends the model to every open
  view slot (MAIN, POPUP, POPOVER; the nested views inherit MAIN's model).
  An event handler that changes bound data can therefore no longer render
  stale by forgetting a call, and an unchanged model sends no MODEL key at
  all (see the wire entry above), so an idle round-trip carries no payload.
  Always on, nothing to activate
! view_model_update( ), popup_model_update( ), popover_model_update( ) and
  the two nested variants now do NOTHING. They stay in the interface so
  existing apps keep compiling and their calls stay harmless - delete them
  when you next touch such an app. What is gone with them is the ability to
  FORCE the unchanged model back onto the client (there was one legitimate
  use: resetting a control that wrote a bound property on its own without
  sending it back - rebuild the view with view_display( ) for that now).
  Cost of the detection: one extra model serialization per event round-trip
+ _bind( json = abap_true ): a bound string that already CONTAINS JSON is
  spliced into the model as a JSON node instead of being sent as a quoted
  string. It exists for a control property that must receive an OBJECT, which
  no typed ABAP value can be: a sap.ui.integration Card manifest has keys like
  `sap.app` and `sap.card`, which are not valid ABAP field names, so it cannot
  be modelled as a structure - and Card.createManifest reads a STRING manifest
  as a manifest URL, so an inline manifest had no way to reach the control at
  all. The flag is outbound only (the client renders such a payload but never
  authors it, and reading a JSON node back would mean writing an object into a
  string field), and a string that does not parse raises instead of emitting
  broken JSON
+ Event arguments: a control-valued event parameter now reaches the backend as
  data. Several UI5 events hand over a control or an array of controls instead
  of a scalar - ViewSettingsDialog.confirm gives filterItems,
  SinglePlanningCalendar.selectedDatesChange a list of DateRange - and those
  could not travel at all: JSON.stringify walks a ManagedObject through its
  circular parent/aggregation graph and threw, so the whole roundtrip body
  failed to serialize. The expression grammar has no loop or lambda either, so
  an app could not project the array itself and was left parsing a localized
  display string (filterString). Lib.normalizeEventArgs now marshals each
  control into an object carrying its ID plus the values of its metadata
  properties, which the app reads from get_event_arg( ) with z2ui5_cl_ajson.
  Which properties exist comes from the control's own metadata - nothing is
  interpreted or renamed - and every argument that is not a control passes
  through untouched, so existing wires are unaffected
+ CONTROL_METHODS: setP13nData (object). The sap.m.p13n panels
  (SelectionPanel, SortPanel, GroupPanel) take their item list only through
  this method - they expose no bindable aggregation for it - so seeding a p13n
  popup previously required hand-written custom JS. It is now a
  follow_up_action( cs_event-control_by_id ) like any other imperative call,
  with the list travelling as one JSON payload
* cc/Storage: the "did the stored value change" check compares by value
  instead of by reference. sap/ui/util/Storage JSON-round-trips what it holds,
  so a structured payload came back as a fresh object on every read, fired
  `finished` on every render, was answered with a re-render and fired again -
  an endless roundtrip loop that made anything other than a plain string
  unusable. A structure or a table can now be stored and read back
! Error output: a 500 response no longer carries only the outermost message. The
  body now holds the full diagnostic in sections - `--- error ---` with the
  message chain, `--- exception chain ---` with one block per entry of the
  previous chain (exception class, own text, the source position it was raised
  at - program / class include / line, what identifies the failing method for a
  CX_SY_MOVE_CAST_ERROR whose text names only the two types - the kernel error
  id and every public exception attribute that carries a value), and
  `--- context ---` with the app / event / draft / url of the failing roundtrip
  and the system (system, client, host, release, user, time). Rendered by the
  new z2ui5_cx_a2ui5_error=>get_text_full( ), which works for any exception
! The error popup shows only the messages of that dump, one per line; the detail
  sections stay one click away behind Details (developer tools Error tab) and in
  Copy, which both carry the untruncated text. Non-framework errors (network,
  client-side, SAP HTML error page) keep the single-line preview
! Error popup design: a square frame instead of rounded corners, and every
  message is its own block with a red rule in front of it rather than one run-on
  paragraph. A fixed content width keeps a long url or class name from stretching
  the box across the screen, and a hint line below the messages names Details as
  the way to the exception chain and the system context - the shortened popup no
  longer looks like all there is. Colors come from the UI5 theme parameters, so
  the popup follows the app theme; the raw-DOM fallback overlay (shown when the
  UI5 core itself cannot render) got the same square frame
* z2ui5_cx_a2ui5_error chains the exception passed as val as its previous. The
  framework's dominant raise pattern (EXPORTING val = x, no previous) used to
  drop everything below x, so the cause of a wrapped error - and its source
  position - never reached the client. Nested causes are still printed exactly
  once, and the chain walk is bounded so a self-referencing previous cannot hang
  the renderer
! The exit z2ui5_if_exit~set_config_http_post -> check_hide_error_details keeps
  suppressing the whole body (now including the system context) as before
- Curated formatter (z2ui5/model/formatter, z2ui5.Formatter): removed round2DP,
  dimensions, stockStatusState, stockStatusIcon and deliveryStatusState. abap2UI5
  is a thin frontend - rounding a number, joining fields and mapping a business
  status to a ValueState/icon are things ABAP finishes, so the app computes them
  and the view binds the result (state="{STATUS_STATE}"). Remaining and unchanged:
  the date helpers (DateCreateObject, DateAbapDateToDateObject,
  DateAbapDateTimeToDateObject) and expandInlineIcons - a JS Date and an icon-font
  glyph are the two things the backend physically cannot produce
! The module's admission criteria are now stated in its header and enforced by
  a CI gate (npm run check:formatter): the export surface must match a manifest
  in which every entry names why it cannot live in ABAP, and no ValueState or
  icon URI may be hardcoded
- BREAKING: removed the component VIEWNAME from z2ui5_if_types=>ty_s_get, the
  structure returned by client->get( ). The framework has never filled it, so
  it always carried an empty string; an app that still reads client->get( )-viewname
  no longer compiles and has to drop the read. This is a deliberate exception to
  the rule "never remove a public symbol from src/02" - recorded here because the
  API snapshot had to be regenerated for it
! All framework-owned apps and the sample repository now call _bind( ) instead of
  the obsolete alias _bind_edit( ). _bind_edit itself stays part of the public API
  and keeps working as a pure alias; custom_mapper_back / custom_filter_back
  are still accepted for source compatibility but no longer evaluated -
  per-direction mapping is gone
* nest_view_model_update( ) / nest2_view_model_update( ) no longer set a
  nest-only flag - the frontend skipped it whenever no nested view happened to
  be open, making the call a silent no-op - and the two slots no longer carry
  CHECK_UPDATE_MODEL on the wire at all. (The delegation to view_model_update( )
  this entry once recorded was itself superseded: all *_model_update methods
  are no-ops now, see the automatic-model-push entry above)
