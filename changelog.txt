abap2UI5 changelog
==================

Legend
------
* : fixed
! : changed
+ : added
- : removed


unreleased
----------
+ START_TIMER repeats on request: a fourth t_arg X (t_arg = event, delay, no-busy flag, repeat flag) arms the timer once and the browser arms the same tick again after every applied response - a user event in between pauses it and it goes on after that event's response, so a poll no longer re-arms START_TIMER on every roundtrip. It keeps running under a popup of the same app and ends with cs_event-stop_timer, a new start_timer, a navigation to another app, a Back/Forward restore, the error overlay or the component's end. Without the flag a timer is the one-shot it always was
+ cs_event-stop_timer (STOP_TIMER): cancels the pending timer tick and ends a repeating timer; as a wired press it stops it in the browser without a roundtrip
! a bound table or structure whose columns carry a namespace (/CWM/XCWMAT) writes each namespace as a level of its row in the model - "CWM":{"XCWMAT":...} where it was "/CWM/XCWMAT":... - on the fast path and on the general road (deep rows, omit_initial) alike, so a row template binds the column relatively as {CWM/XCWMAT}: the name as it was, {/CWM/XCWMAT}, is an absolute path in UI5 and rendered an empty cell whose edits went nowhere. Edits come back onto the component (row deltas, whole values, nested tables); a column named like a namespace of its neighbours (CWM next to /CWM/...) gives way to the namespace object. The JSON of every other table is byte for byte what it was. _bind( val = ... tab = ... tab_index = ... ) of a namespaced cell returns /T/0/CWM/XCWMAT instead of /T/0//CWM/XCWMAT
+ z2ui5_cl_ui5_view_builder=>component_path( name ): the binding path of a column relative to its row - /CWM/XCWMAT gives CWM/XCWMAT, every other name comes back unchanged - for a row template over a table whose columns are only known at run time
+ client->get_start_param( name ): one start parameter of the page, whichever way the app was started - the URL query first (sap-startup-params unpacked), then the launchpad's startupParameters, then the query of the launchpad intent in the hash; the name in any case, the value as the source carries it
+ nav_app_leave( keep_messages = abap_true ) and nav_app_call( keep_messages = abap_true ): the message toasts and boxes the app queued in this roundtrip are shown after the target app has rendered instead of being dropped with the screen they were queued on. Not supplied, nothing changes
! a START_TIMER tick whose main( ) left the app unchanged writes no draft: the response names the draft it continued, and only its time is renewed (at most every five minutes, so a long quiet poll keeps it). A screen that polls every two seconds wrote a row of its whole state per tick. The frontend marks a tick on the wire (S_FRONT.TIMER); every other event still answers a new draft id, also when nothing changed, as the protocol asks
* a click that met a START_TIMER tick in flight was dropped - at random, on every polling screen, and without a trace when the tick was a no-busy one. It is held back now and sent once the tick's response is applied, under the draft id that response named; while it waits, the timer does not tick again. A second click meets the busy guard as a second click always did
+ z2ui5_if_ui5_exit=>ty_s_http_config_post-draft_keep_per_chain (2 by default, 0 switches it off and keeps every draft until its expiry as before): N keeps the last N drafts of the chain an app's roundtrips write and deletes the one at depth N + 1 on every save, at constant cost. 2 is the minimum and what a polling app wants (the retry of a lost response continues the draft before the newest one). The drafts of the app stack, the draft of an app state link (app_state_get_href) and of a route restore are never deleted, nor any draft of an app whose app state hash is active. The draft store interface z2ui5_if_ui5_draft_store has two new methods for it, prune_chain( ) and touch( ) - a host's own store implements them
* a bound field whose name carries a namespace (/ABC/FIELD - the fields of an industry solution or a customer namespace in a DDIC table, a component of a structure built from one) binds under /PARENT/ABC/FIELD instead of /PARENT//ABC/FIELD: the empty segment made UI5 resolve the binding to the parent, left the value out of the model, and a bound table of fixed values raised MODEL_FAST_PATH_TOKEN_LOST on the first rendering (table-maintenance's edit popup over MARA). A bound table the model cannot place takes the general serialization instead of raising
+ client->check_nav_pending( ): whether this roundtrip already ends in a navigation - true once main( ) has called nav_app_call( ) or nav_app_leave( ). The public form of get( )-_s_nav-check_call / check_leave, for a base class that must not arm a timer, convert data for output or clear messages for a screen the app is about to give away
+ nav_app_call( tag = ... ) and client->get_nav_tag( ): the caller names why it calls, and reads that name on the roundtrip the called app comes back on - an app that opens one popup class for several purposes tells the returns apart without a flag attribute per purpose and without a CAST in a TRY. The tag is the caller's and travels in its own draft; the called app is unchanged and never sees it
* the start app tells a class that cannot be loaded (a syntax error in it, a missing dependency) from one that does not exist - "could not be loaded" with the reason instead of "does not exist or does not implement z2ui5_if_app"; such a failed check is not cached any more, so the corrected class passes on the next try
+ message_box_display( icon = ... ): the icon of the box is a parameter again - a sap.m.MessageBox.Icon name or a sap-icon:// URI; it had left the method with the pure UI5 options in 2026-09 by mistake
! BREAKING: the custom controls (z2ui5.cc) are a bundle of their own - ?z2ui5-bundle=cc, loaded once per page before the first view, nested view, popup or popover that names one (xmlns:z2ui5="z2ui5.cc" under any prefix, a z2ui5/cc/<Name> in the view, or the sibling BSPs z2ui5_cci / z2ui5_ccc) - and no longer part of the frontend bundle every page loads: that one is 191 KB where it was 247 KB (56 KB gzipped, was 70 KB). 19 of 763 sample apps use a control. Breaking only for JavaScript OUTSIDE a view that requires z2ui5/cc/<Name> on a page whose views name no control - it has to load the bundle first; where the files are served one by one (the BSP, the cloud app) nothing changes
! the first page load is shorter: the page the node serves names the frontend bundle in a <link rel="preload"> and sap.m on the bootstrap tag (data-sap-ui-libs), so both load while UI5 boots instead of one after the other behind it - measured in Chromium on a cold cache, the first view is on screen about 0.5 s (some 15 to 20 %) earlier. No hint where the bundle's URL cannot be known in advance (a path ending in a slash), and no second data-sap-ui-libs when the exit set_config_http_get already sets one
! the frontend is delivered minified - comments and whitespace go, the identifiers stay (tools/app2abap, terser without compress and mangle): the bundle is about 250 KB where it was 354 KB (71 KB gzipped, was 82 KB), and the class that holds it a good third of its size. A stack trace still names the real functions; it no longer shows the lines of bundle/webapp
! the model: a bound table whose row type has an .INCLUDE or a TIMESTAMP / TIMESTAMPL column is serialized on the fast path as well (the output is byte for byte what it was), and the tables of a model are spliced into it in one pass instead of one copy of the whole model per table
* window_bind_tab( total = <a value that is no attribute>, e.g. lines( t ) ) ran the binding search's worst case on every call - three searches and a rebuild of the attribute table - and left the bind service holding a row of the table it had just cleared; the total is looked up without touching the table now
! the user exit's set_config_http_post is asked once per request, not up to three times, and a response that is not the page no longer assembles the page's config (the CSP text among it) for its five headers when no exit is installed; z2ui5_cl_ui5_http_handler prepares its context once per request
! frontend: a slot and its model remember the response that built them by a token instead of holding the whole response - the model and the view XML of a response are released once the screen has moved on (about 200 KB per 1,000 rows of a bound table and slot); the request text is released once the developer tools have counted it
! frontend: one abort mechanism per request (one AbortController and one timer, cleared when the request settles) in place of three browser-dependent paths - a finished request no longer leaves a ten-minute timer behind. An abort that is neither the timeout nor a newer request reads as the network error it is
- BREAKING: the frontend action targets nothing writes since protocol 3 - CONTROL_GLOBAL ROUTER sync and the VIEW_SLOTS methods display and updateModel (VIEW_SLOTS destroy, the wired close of a popup, stays); z2ui5_if_ui5_types=>cs_global_target-router and the unread ty_s_response-s_front-protocol go with them. The developer tools' recorder names its two counts viewCount and actionCount (were systemActions and customActions)
! BREAKING: client->hash_set( ) and hash_replace( ) (cs_event-hash_set / hash_replace, experimental) write the hash only for an app that owns it - a listener registered with cs_event-hash_attach_changed, hash_routing off - and the value is the whole app hash. Without a listener, and under hash_routing, nothing is written and the frontend says so in its log. Until now the value was appended to the hash the page had: with history.pushState, which hasher's cache did not see, so the next Back went nowhere; behind the route in KEEP mode; and an app that wrote a whole route on every roundtrip grew its URL (#/repo/1/repo/1). An app that writes a hash registers the listener in view_display( ), as the ten sample apps that write one already do
* windowed tables (window_bind_tab): the requests of several tables on one page no longer overwrite each other while a roundtrip runs - there was one place for all of them, the last one winning, and a request a list sent while its view was still being built was dropped when it was due. Each table keeps its own now, and they go out one after the other
! an event a control fires while its view is being built - a z2ui5.cc.Storage answering from its rendering with the value it found, an afterRendering an app wired - reaches the backend on every roundtrip now, after the response that built the view. Until now it was sent at once on the first roundtrip, where it superseded the response that was building the screen, and was dropped without a word on every later one unless its wire carried check_queue_last. The first roundtrip marks the app busy like every other one. An app that answers such an event with a view that fires it again is stopped after 25 of them in a row, with a line in the log
! BREAKING (wire, protocol 3): a request that starts an app names what the URL hash asks it to restore as S_FRONT.ROUTE - { APP, DRAFT } for a route #/app/<CLASS>/<DRAFT>, { APP_STATE } for an app-state link - parsed by the frontend's router (Router.startRoute). The backend no longer reads a route out of S_FRONT.HASH: its own parser of the launchpad separator, the stacked slashes of older URLs and the namespaced class is gone (six methods of z2ui5_cl_ui5_handler), which had to be kept equal to the router's by hand. HASH still travels with every request for the app (client->get( )-s_config-hash)
! BREAKING (wire, protocol 3): the response says what the screen is and what to do on it in three sections of S_FRONT - VIEWS (one entry per slot the roundtrip changes: { XML, OPT } for a display, { DESTROY: true } for a teardown), NAV (the URL intent, the options of the router's sync) and ACTIONS (the app's follow-up actions) - where S_ACTION carried the lists T_SYSTEM (["VIEW_SLOTS","display","MAIN",...], ["ROUTER","sync",{...}]) and T_CUSTOM. The frontend applies the views in its own order, MAIN first, so the backend sorts nothing; a section that says nothing is absent. An app changes nothing - a frontend or a tool that reads the response does
! BREAKING (wire, protocol 3): the backend states the teardown of POPUP and POPOVER for every app hop and every app start, as their VIEWS entries; the frontend no longer takes the two slots down by itself when a response names another class (it could not see a hop to another instance of the same class, which the backend covered as a special case). A new MAIN view still takes them down with it - that rule is the frontend's alone now, and the backend no longer drops a popup_destroy( ) next to a view_display( )
! BREAKING (wire, protocol 3): the flags of an event wire travel as one object behind the event name - .eB(['LIVE_CHANGE',{queueLast:true,noBusy:true}]) - and no longer as positions [4] and [5] of the event array behind three slots that were always false. client->_event( s_ctrl = ... ) writes the new form, so an app changes nothing; a view that writes the array by hand writes the object, and a positional flag is reported in the log and not read. z2ui5_if_ui5_types=>c_protocol and the frontend's PROTOCOL are 3
- BREAKING: _bind_edit( ), view_model_update( ), nest_view_model_update( ), nest2_view_model_update( ), popup_model_update( ) and popover_model_update( ) of z2ui5_if_client - none of them did anything of its own: _bind_edit( ) was an alias of _bind( ) (binding always writes back), and the model is pushed automatically whenever main( ) changed it. Write _bind( ) in place of _bind_edit( ) with the same parameters (custom_mapper_back and custom_filter_back were no longer evaluated and go), and delete the *_model_update( ) calls
- BREAKING: the offline queue (experimental in 1.149.0 and 1.150.0) - cs_event-offline_queue, the frontend's core/Offline.js and the replay in core/Server.js. An edge case the framework does not carry: an event that cannot reach the backend ends in the error overlay with its Retry, as every other one. Sample 543 is removed with it
! BREAKING: the windowed table of 1.149.0 and 1.150.0 is app-driven - window_bind_tab( val total event window ): the app holds the rows it has loaded and loads, sorts, filters and counts them itself, the way an OData service answers $skip, $top, $orderby and $filter. The browser's requests (more rows, a sort, a filter) arrive as the app's event with z2ui5_if_client=>ty_s_window_request in get( )-r_event_data (cs_window_reason MORE / SORT / FILTER). t_sort and t_filter of window_bind_tab( ) and window_get_row( ) are removed - val is what the browser shows, a row index is its row
- the server-side sort and filter of windowed tables, the window index of a row delta and the draft's frame of kept tables (z2ui5_cl_ui5_srv_window is the request parser now)
! one pull is a running installation: the ICF node /sap/bc/z2ui5, its handler z2ui5_cl_ui5_icf_handler and the BSP Z2UI5 for the launchpad are part of this repository (src/03) - they were the branch standard_new of abap2UI5/frontend, a second repository to pull. The node and the BSP keep their names, the handler is renamed (it was z2ui5_cl_lp_handler); an installation that has that repository removes it from abapGit WITHOUT deleting its objects and pulls this one
+ the branch cloud: abap2UI5 for ABAP Cloud, generated from main on every push (auto-cloud.yaml, tools/build-cloud.mjs) - the HTTP service, its handler and the IAM objects in place of src/03, the app as a Fiori project in app/, the ABAP language version in the abapGit descriptor. It takes the place of the branch cloud_new of abap2UI5/frontend
- BREAKING: z2ui5_if_exit, the former name of the exit interface, is deleted, and the framework no longer looks it up - an exit class that writes INTERFACES z2ui5_if_exit writes INTERFACES z2ui5_if_ui5_exit instead and names its two methods z2ui5_if_ui5_exit~set_config_http_get / ~set_config_http_post (same parameters, same types). Until it does, it does not compile and the installation runs on the shipped defaults: no custom Content-Security-Policy, theme or bootstrap
- BREAKING: z2ui5_cl_http_handler, the former name of the HTTP entry point, is deleted - an ICF node or a handler class that still names it names z2ui5_cl_ui5_http_handler (the same methods, it was an empty subclass), or uses the node /sap/bc/z2ui5 with its handler z2ui5_cl_ui5_icf_handler this repository delivers
- BREAKING: z2ui5_cl_xml_view, z2ui5_cl_xml_view_cc, z2ui5_if_types and the seventeen z2ui5_cl_pop_* popups are no longer part of the core - they moved, unchanged, to the extension repository (abap2UI5/frontend, which holds what abap2UI5-ext held as well). A system whose code still names one installs that repository next to abap2UI5. src/99 is gone
! the BSP Z2UI5 is generated from app_source/webapp by npm run app2abap and committed (src/03/02), like src/01/03; a namespace rename (build-rename) covers the ICF node, the handler and the BSP as well, so rename_<name> is the whole installation
! the embed control stays in abap2UI5/embed-control, with its tests, its examples and its npm package (0.4.0 there: the shell the bundle creates the app for) - this repository copies it from a pinned commit into the page and the BSP (node/setup/fetch-deps.mjs, tools/deps/), and app_npm is gone: app_source takes the control from npm
- the delivery into abap2UI5/frontend: tools/build-branches.mjs, frontend_check, frontend_deploy, frontend/embed and the dependency on @abap2ui5/embed-control 0.3.0 - that repository is the extension now
* a view that fails to build no longer runs the follow-up actions of its response under the "App Terminated" overlay - a START_TIMER in it kept sending roundtrips for an app that had ended, and a parked hash change sent one
! the frontend's classes are taken off window on every page; a class of the frontend cannot be extended before UI5 1.120 with that (it could on the backend's own page) - extending them was never a supported way, a customer's own control lives in its own BSP and extends sap/ui/core/Control
- frontend: Lib.deriveOsName (no caller) and the state field ownsHash (always equal to ownsPage; componentData.ownsHash is still read)
! the minimal app of the backend's page (app_source) is the component z2ui5 with the launchpad entries in its manifest, and its view is the control alone - the sap.m.Shell around it is gone again: an app without a Shell of its own is as wide as the window, as before the page was changed. A launchpad tile's parameters are read by the bundle (core/Embed.js), and on a page handed to the app the mobile setup is the sap.m.App's again
+ npm run express:live: the dev server with the frontend bundle served straight from bundle/webapp - edit a file and reload the page, without app2abap and a transpile in between (the page's own app and the control stay the built ones)
+ the page asks for the frontend bundle by its version (?z2ui5-bundle=<build hash>, the control's new bundleVersion) and the backend lets the browser keep that answer (max-age, immutable) - a start costs no request for the frontend once it is cached; a bundle asked for without the version revalidates as before
! the end of the frontend bundle - the z2ui5/embed module and its create( ) - is a file of its own, bundle/tail/embed.js, formatted and linted like the frontend; the handler only writes the request's path into it
! the frontend has one mode: its component is always created by the embed control, so the branches for a page of its own are gone (componentData.embedded is no switch any more) - what is left is whether the host handed the page over (ownsPage). A component created without ownsPage no longer takes the hash, the title or the busy indicator of the page
* on the backend's own page an app's SET_FOCUS and the first page's autofocus work again from the start - the focus guard of a host's page applied there too
! the embed control is a shell: it loads the bundle and renders what the bundle's z2ui5/embed module creates (create( ), bundle/webapp/core/Embed.js) - the component, its component data and the style of the area come from the backend, for a freestyle app, a custom page or section of Fiori elements and the backend's own page alike. Its stylesheet is gone, and with it GET <node>/embed/Container.css; ownsHash is gone (ownsPage). @abap2ui5/embed-control 0.4.0 needs this release - 0.3.0 keeps working against it
! src/01/03 holds five generated classes instead of about 140: one per text the HTTP service serves (z2ui5_cl_ui5f_bundle, _devtools, _page, _page_css) and the facade z2ui5_cl_ui5f_preload - the backend no longer joins the frontend from one class per file on every request, and a pull activates about 135 objects fewer. The classes of the single files (z2ui5_cl_ui5f_*_js, _xml, ...) are gone
! app/ is bundle/: the folder is the source of the bundle the backend serves (?z2ui5-bundle), no longer a UI5 app of its own - webapp/index.html, the launchpad inbound and sap.cloud of its manifest, its start scripts and the direct start of the component (componentData.checkLocal) are gone; the component is created by the embed control, on the backend's own page too
! the abap2UI5/frontend branches cloud, cloud_v2, standard and standard_v2 and the renamed variants standard_<name> / standard_v2_<name> are not built from this repository any more - they shipped the frontend as an app of its own; cloud_new and standard_new are built as before, and the four are to be built from app_npm
! the page the HTTP service answers a GET with is a minimal UI5 app around the embed control: a component with one XML view whose one element is a z2ui5.embed.Container, which loads the frontend from the node (?z2ui5-bundle), the way the abap2UI5/frontend branches standard_new and cloud_new start it - the page no longer carries the frontend in its inline script (about 14 KB instead of 700 KB; the bundle is a cached file of its own). The roundtrips of an app on that page go to the page's path without the page's query
+ app_source/: that app as a UI5 project of its own, with a standard index.html and the control as the npm dependency @abap2ui5/embed-control - the page of the HTTP service and the BSP are written from it
! developer tools: an embedded component that owns the page (componentData.ownsPage) captures the page's console again - the page is the app's
- BREAKING: z2ui5_cl_http_handler, the former name of the HTTP entry point, is deleted - an ICF node or a handler class that still names it names z2ui5_cl_ui5_http_handler (the same methods, it was an empty subclass)
* @abap2ui5/node-runtime: open-abap-core moves to 1e83502 - cl_abap_typedescr=>describe_by_data_ref raises REFERENCE_IS_INITIAL instead of a JavaScript TypeError, so the RTTI helpers of z2ui5_cl_ui5_util_context call it with EXCEPTIONS on every target


2026-11-20 v1.150.0
-------------------
! drafts: a blank owner (a row from before the UNAME column) is no longer read, found, counted or overwritten as anyone's - the tolerance kept through 1.149.x for the upgrade window is gone, as planned
! Repositories moved and renamed: the embed control is abap2UI5-addons/embed-ui5-control, the mobile shell abap2UI5-addons/embed-mobile, the web component frontend abap2UI5-addons/embed-webcomponent, the Excel add-in abap2UI5-addons/embed-excel, the playground abap2UI5/browser-playground, the legacy utilities abap2UI5/abap2UI5-obsolet; comments and docs follow
* window_bind_tab( ) on a table behind a data reference: an edit in the browser (a checkbox, a cell, the selection of a TableSelectDialog) reaches the app - the frontend shipped the whole /<attr>/* node instead of its row delta, and the backend never writes a windowed table back whole, so the edit was dropped
* RTTI helpers of z2ui5_cl_ui5_util_context: an initial reference no longer ends the request in the runtime error REFERENCE_IS_INITIAL - rtti_get_typedescr_by_data_ref, rtti_get_t_attri_by_oref and rtti_get_t_attri_by_any raise z2ui5_cx_ui5_util_error RTTI_REFERENCE_IS_INITIAL, rtti_check_table_standard and rtti_get_flat_components answer false / empty; the GUID_CREATE fallback catches a message the module sends
* @abap2ui5/node-runtime: abap2ui5-own-apps keeps the host's DDIC that transpiler 2.14 on writes into output/project/_ddic.mjs and imports it before the host's classes - 1.149.0 took the file for a class named like one of the package's and refused every host with a table or data element of its own
