unreleased
----------
* The start page survives its second roundtrip. z2ui5_cl_ui5_app_start holds its client PUBLIC, and the model service's dissolve walk followed it into the framework's own object graph - client, action, handler, app container and round again - which put 300 attribute rows under CLIENT-> into every draft of the start page (a hello-world app has one row). One of those rows resolved to the container's own row table, and the detach the save does for every data reference (unreleased, above) cleared THAT one too, so the draft carried an empty MT_ATTRI and the next request - any button on the start page - found no rows to load. The walk skips the framework's client object now (nothing an app can bind lives behind it), the save never detaches the row table itself, and a handler test drives the start app through a first start and an event on the draft it wrote. Every other app of the ecosystem holds its client protected, as the template says, and was never affected
* The frontend loads the OData v2 client on first use instead of on every start. sap/ui/model/odata/v2/ODataModel was a sap.ui.define dependency of two modules, and with it the whole sap/ui/model/odata cluster plus sap/ui/thirdparty/datajs - which is not in the core preload - was fetched and executed on every cold start of every app, for the few that switch their default model or issue SET_ODATA_MODEL. Lib.requireODataModel( ) loads it when one of those two asks; a follow-up action that loads something hands its promise back through eF( ) and the custom-action runner awaits it, so an action queued behind SET_ODATA_MODEL in the same response still finds the model in place. Also: Router.hrefFor( ) and the parse/patternFor exports had no caller left (the share link is composed by the backend since app_state_get_href) and are gone; the devtools console caps the nodes it serializes for one entry, where a map-shaped object was stringified in full before the 2000-character cut
* request_parse_body no longer copies the request body to find out whether it is empty. The emptiness test was condense( val ) IS INITIAL - which built a second, condensed copy of the whole body on every POST, a mass-edit delta of megabytes included, to test the copy. `val CO space` answers the same question at the first character that is not a blank, and keeps the 7.02 built-in out of the predicate operand for free. cc/Timer.js drops its timer id after clearing it on a checkActive=false render, so a stale id is not kept around
* STORE_DATA writes nothing after a payload it could not resolve. A string argument that is no model path, or a path with nothing bound under it, was logged - and then the handler went on with an empty payload and called remove( undefined ) under the app's prefix, so the error left a "undefined" key removed from storage behind it; a missing argument took the same route. The handler returns after the log now, and a call with no argument at all is logged as such. The ABAP Doc example of cs_event-store_data is corrected with it: on a view wire the binding has to be written as |${ client->_bind( ms_storage ) }| - a bare {/MS_STORAGE} travels raw into the handler expression, where UI5 reads it as an object literal and the wire never fires (samples 327 had to spell it that way); a handler resolves both spellings, so only the wire form was wrong. building-apps.md names check_no_busy next to check_queue_last, the pair a per-keystroke wire wants, which the guide had left out
+ z2ui5_if_ui5_draft_store - the draft persistence behind an interface, swapped with z2ui5_cl_ui5_srv_draft=>set_instance( ). The framework's session state is the one thing a host outside an SAP system cannot bring with it: the shipped store writes Z2UI5_T_01 through Open SQL, which a NodeJS host satisfies with a private SQLite that no other part of that host can see or transact with. An implementation supplies the seven methods (count_entries, count_entries_total, create, read_draft, read_info, check_exists, cleanup) and decides where the rows live - a CAP project puts them in a CDS entity and gets its own connection, transaction and authorization for free. The owner-binding contract is in the interface's ABAP Doc, including the one part an implementation must not get wrong: a read of somebody else's draft answers the same NO_DRAFT_ENTRY_OF_PREVIOUS_REQUEST_FOUND a missing one does, so a caller cannot tell a foreign draft from an absent one. Nothing changes for a system: get_instance( ) hands back a fresh instance of the shipped store per call, byte-identical to what the direct calls did
+ z2ui5_if_ui5_app_serializer - the app-state serialization (all_xml_stringify / all_xml_parse on z2ui5_cl_ui5_app_cont) behind an interface, swapped with set_serializer( ). It is the other half of the same problem: the default is CALL TRANSFORMATION id over S-RTTI, which has no counterpart outside ABAP, so a host that cannot transform has nothing to fall back on. What an implementation owes is a round trip, not a format - parse( stringify( container ) ) must answer a container the framework can go on with; the string in between is its business. Both ends are typed REF TO object rather than REF TO z2ui5_cl_ui5_app_cont: an interface here may not reference a class (intf_referencing_clas) and naming it would close a cycle, since the container is what calls the interface. The default is the existing transformation, unchanged
* The view builder survives a runtime with no codepage class. z2ui5_cl_ui5_util_context=>conv_get_string_by_xstring / conv_get_xstring_by_string reach cl_abap_conv_codepage first and the classic CL_ABAP_CONV_* pair second, but the fallback was raised from inside the first CATCH - so on a runtime where neither exists, the second failure escaped as an unhandled exception from within an exception handler instead of as UNSUPPORTED_CODEPAGE_API. The caller that pays for it is z2ui5_cl_ui5_view_builder, which builds its control-character escape set at class level: the failure took the view build with it before any app code ran, and a host cannot catch what never became a class-based exception. The fallback is its own TRY now, both failures are chained into UNSUPPORTED_CODEPAGE_API, and the builder degrades with CLEAR gv_escape_controls - it stops escaping control characters and renders the view. Found on a transpiled NodeJS runtime, where it presented as a HANG rather than an error: cap2UI5's transpiled core blocked on the first roundtrip for weeks while every gate stayed green, because the shape only exists where the codepage class is absent and no CI runs there
+ S_FRONT.PROTOCOL on every response, from z2ui5_if_ui5_types=>c_protocol, and app/webapp/core/Server.js compares it against its own PROTOCOL before reading anything else. It is not the product version and does not move with a release; it moves when a response can no longer be read by a frontend written for the previous number - the S_ACTION envelope replacing S_FRONT.PARAMS was such a change, and it is the reason this exists. The two halves ship together here and not everywhere: a port of this framework, a pinned webapp or a third-party shell can pair a backend and a frontend of different ages, and the failure mode was the worst available - the frontend looked for a key the backend no longer wrote and rendered its empty result. A mismatch is now reported to the user; a response WITHOUT the field is let through, because a backend older than the field cannot be told apart from one that is merely older. Raise both halves in the change that breaks the wire
+ The transpiled framework is also published as the npm package @abap2ui5/runtime, from two steps appended to backend-prebuilt.yaml. That workflow already downports, transpiles and proves the tree with the unit suite for the release tarball, so the package is packed from the SAME build rather than from a second 30-minute one: node/output, node/setup/setup.mjs (the hook output/init.mjs imports by the relative path abap_transpile.json fixes) and app/webapp, at the framework's own version - node/package.json is the manifest. It is a second delivery of one build for a different consumer: the tarball is resolved by name from a GitHub release, which suits a tool that downloads it, while a host that is an ordinary Node project - a CAP plugin, a serverless function - declares dependencies in package.json and has `npm i` already. What differs in the contents is the frontend: the package carries app/webapp and not node/deps or node/downport, because a host that RUNS the framework needs the shell from the same commit as the backend - the guarantee z2ui5_if_ui5_types=>c_protocol cannot give a host that pairs the halves itself. The .tgz is uploaded as a workflow artefact on every run; npm publish happens only when the organisation has an NPM_TOKEN, warning loudly and staying green without one, and the release was created before this workflow started, so neither a registry failure nor a missing token can touch it. What the package promises is only what the transpiler output promises: the shape of that output is @abaplint/transpiler's, not this repository's, and a host that reaches into it should gate that coupling with a test of its own
- BREAKING: cs_event-wizard_set_next_step is removed, and with it the WIZARD_SET_NEXT_STEP handler in the frontend (evWizardSetNextStep in app/webapp/core/actions/ViewOps.js, so src/01/03 is regenerated). It bundled the two calls a UI5 controller makes on a Wizard - discardProgress( oStep ) followed by oStep.setNextStep( oNext ) - into one fixed pair. Both methods are on the frontend CONTROL_METHODS whitelist, so the same flow is two ordinary control_by_id calls, which additionally reach goToStep - a step the bundled event could not express at all: follow_up_action( val = cs_event-control_by_id t_arg = VALUE #( ( `wizard` ) ( `discardProgress` ) ( `step1` ) ) ) then the same with ( `step1` ) ( `setNextStep` ) ( `step2` ). Zero usages in the ecosystem - the Wizard sample (samples z2ui5_cl_smp_app_202) already drives the flow through control_by_id and is the migration example
- BREAKING: the obsolete spellings of the URL API are removed - the methods client->set_push_state( ) and client->set_app_state_active( ), and the constants cs_event-set_nav_routing and cs_event-clipboard_app_state. The first three are pure renames and a caller changes only the name: set_push_state( ) -> hash_set( ) (HashChanger#setHash; "push state" described the old history.pushState implementation the HashChanger-backed write replaced), set_app_state_active( ) -> app_state_set_active( ) (the family prefix, so it sorts next to app_state_get_href( )), cs_event-set_nav_routing -> cs_event-hash_routing (it is the HASH that is routed; nav_* is app-to-app navigation). The constants cs_event-set_push_state and cs_event-set_app_state_active go with their methods - they were alias spellings of cs_event-hash_set and cs_event-app_state_set_active, so the obsolete run of the hash_*/app_state_* family is now empty. All of them shared their wire value with the surviving name, so nothing moves on the wire and the two delegating method bodies are gone rather than reimplemented. hash_set and app_state_set_active therefore still carry the WIRE values SET_PUSH_STATE and SET_APP_STATE_ACTIVE, and must keep them: a draft can hold a queued action, so renaming a value is not the same kind of change as renaming a constant. cs_event-clipboard_app_state is the one that is not a rename: it composed the share link in the BROWSER and could only put it on the clipboard, while app_state_get_href( ) hands the same link to ABAP - so the app can show it in an Input, mail it or render it as a QR code - and copying it is then cs_event-clipboard_copy with that string as t_arg. Its frontend handler (evClipboardAppState in app/webapp/core/actions/Browser.js) goes with it, so src/01/03 is regenerated; Router.hrefFor stays, it is what the backend composition mirrors. Zero real callers in the ecosystem: samples, samples-controls and samples-stack name none of the four in code. API snapshot regenerated
- BREAKING: the view parameter of client->_bind( ) and client->_bind_edit( ) is removed. It was marked obsolete at both declarations and had been INERT for as long as it carried that mark - it was never passed on internally and never reached the model, a leftover from the time each view slot owned a model of its own; today one model serves every open slot, so there is nothing for it to select. A call that names it fails at compile time and the migration is to delete the parameter, nothing else: _bind( val = ms_data view = client->cs_view-popup ) becomes _bind( ms_data ), and the binding it returns is the same string it already returned. Zero callers in the ecosystem - samples, samples-controls and samples-stack do not name it and never did in their git history; the only in-repo caller was _bind_edit( ) handing it to _bind( ). cs_view itself stays: it is the view slot of follow_up_action( ) and _event_client( ), where it does select a slot. API snapshot regenerated
- BREAKING: client->_event( s_ctrl-check_allow_multi_req ) is removed, and with it the component from ty_s_event_control - an app that names it does not activate any more. It sent the event while another roundtrip was still running and let the responses land in any order, which is the wrong shape for the per-keystroke wires it was reached for: the newest response is the only one that may commit, so every earlier roundtrip was work the backend did to have its answer thrown away. check_queue_last is the replacement for that case and is strictly better at it - one roundtrip in flight at a time, order preserved, the backend ends on the control's current value. Position [2] of the event array stays reserved and is always false, so nothing behind it moves and custom JS that builds the array keeps reading the same slots; View1.eB ignores a truthy value there. The request sequencing in Server.js stays as it is - a Back/Forward restore and reset( )'s teardown bump the same sequence and always did
- BREAKING: client->message_toast_display( ) and client->message_box_display( ) carry only what an ABAP app decides, and every parameter that was a PLAIN sap.m option is gone: width, my, at, of, offset, collision, autoclose, animationtimingfunction, animationduration, closeonbrowsernavigation and class on the toast, textdirection, icon, closeonnavigation, dependenton and contentwidth on the box. They are set on the CONTROL now - follow_up_action( cs_event-control_global ) calls sap.m.MessageToast / sap.m.MessageBox itself, the display method IS the box type, and a t_arg that starts with a brace travels as real JSON, so the last argument is the option object of that UI5 API 1:1: client->follow_up_action( val = client->cs_event-control_global t_arg = VALUE #( ( `MESSAGE_BOX` ) ( `error` ) ( `Not saved.` ) ( `{"contentWidth":"30rem","icon":"WARNING"}` ) ) ). Both paths end in the same frontend code, onClose stays a backend event name on either, and the wired form composes its text on the client ({0} placeholders) without a roundtrip - so nothing an app could express before is out of reach. What stayed is the ABAP side: text TYPE any, type, title, styleclass, actions, emphasizedaction, initialfocus, details and onclose on the box, text, duration and onclose on the toast. A caller that passed one of the removed parameters fails at compile time and moves the option into the JSON object; samples 381 and 512 show the two halves side by side

! _bind( json = abap_true ) is refused at BIND time on an attribute that cannot hold JSON text. The flag says "this value IS JSON", which only means anything for an ELEMENTARY attribute: the serializer parses the value and splices the result in as a node. Handed a structure, the parse used to be fed whatever that structure converts to - on a flat one a character conversion that SUCCEEDS, and then fails with a message about the text rather than about the bind; handed a table, the conversion itself was what failed. Either way the error arrived one layer below the mistake, inside main_json_stringify. z2ui5_cl_ui5_srv_bind now raises z2ui5_cx_ui5_util_error where the app made the call and names the attribute, on the first bind and on a later one alike (check_json turns on through both paths). A CELL bind is unaffected and stays as documented - check_json is stored on the cell and has no effect there. Nothing that worked stops working: an attribute that could be parsed is elementary by definition
+ client->_event( s_ctrl-check_no_busy ) - a per-wire flag that keeps the GLOBAL busy indicator down for the wire. The roundtrip is unchanged - one request in flight at a time, the busy STATE is still set, so the guard, check_queue_last, the parked hash routing and the request sequencing all keep working - only the full-screen overlay is not raised. It is the second half of a per-keystroke wire: the FIRST roundtrip raises the overlay after the usual 1s delay, and every keystroke that lands on a roundtrip already in flight raises it with NO delay, because a dropped CLICK needs that feedback at once - so a live search flashed the overlay over the very field being typed into, from the second character on. check_queue_last stops the keystrokes from being lost, check_no_busy stops the overlay from blinking; the pair is what a liveChange/liveSearch wire wants. The flag is per WIRE, not per roundtrip: a click dropped while a silent roundtrip runs still gets its overlay, and the response's hide( ) is unchanged. Appended at the end of ty_s_event_control and at position [5] of the event array, behind check_queue_last - which a wire carrying only this flag emits as false rather than closing the gap, so no position ever moves. Samples 059 (live search over a large table) is wired with the pair
+ client->_event( s_ctrl-check_queue_last ) - a per-wire flag for the per-keystroke events (liveChange, liveSearch, sliderChange): while a roundtrip is in flight the LAST event fired on the wire is kept and dispatched once the response has landed, instead of being dropped - one roundtrip in flight at a time, order preserved, the backend ends on the control's current value. The busy guard dropped every keystroke typed while a roundtrip ran, the last one included, so the backend stayed at the value of the last COMPLETED roundtrip while the control showed the current one (samples-controls 280, sap.m.TextArea: `abc` typed at once left the bound field at `a` until the user paused and typed again). Appended at the end of ty_s_event_control and at position [4] of the event array, behind the existing flags. No debounce: every pause of one roundtrip still costs one roundtrip
+ Every release carries the transpiled Node backend as an asset. backend-prebuilt.yaml runs when the release is published (and on dispatch with a tag, to re-attach for a past one): it checks out the tag, downports, transpiles, runs the unit suite and attaches backend-<version>.tar.gz - node/downport, node/output and node/deps without their .git directories, plus a backend-manifest.json at the root naming the version, commit, build time, node and transpiler versions. npm run pack:backend (node/setup/pack-backend.mjs) is the packer. abap2UI5/mcp-server's build_backend downports and transpiles the whole framework itself on its first full build, tens of minutes; with the asset a consumer downloads what this repository had already built. The asset name and the manifest are a contract that repository reads, and the -702 release gets none - it is the downported sources, and the backend is built from the same commit anyway
* A POST with no body at all is answered like a POST carrying `{}`. Both name no S_FRONT, so both take the system-startup path - but the empty one reached the JSON parse, which refuses an empty string, and the availability probe a monitor or a load balancer sends came back as the framework's own 500 while `{}`, `null` and even `42` all rendered the start page. The shape is not hypothetical: node/srv/express.mjs substitutes an empty buffer for a missing body, and a gateway that unwraps the envelope can leave nothing behind. A body that is NOT empty and not JSON stays a 500 - that is a client sending something wrong, and it is worth seeing
* message_box_display( ) survives a structure whose component names collide with the message vocabulary. The message detection maps every component of whatever an app hands over BY NAME - a component called TEXT, ID, NO, TYPE or V1..V4 is taken as that part of a message - and it assigned the value without asking what it is. A business structure carrying a `text TYPE string_table` (a long text) or a nested structure under one of those names therefore reached a MOVE of a table into a string, which is not a class-based exception but a runtime error (OBJECTS_MOVE_NOT_SUPPORTED on a system, "table, no header line" in the transpiled runtime): nothing between there and the app's own main( ) catches it, so the box that was supposed to REPORT a problem ended the roundtrip as a 500. The shape is decided BEFORE anything is assigned now - the same rule the row delta follows in z2ui5_cl_ui5_srv_model=>delta_apply_field, and for the same reason, that a runtime error cannot be caught after the fact. A component that is not printable is simply not a message part: the entry ends up without a text, it is dropped, and the DATA renderer shows the whole structure including that component - which is what the app wanted to see. Two more of the same shape went with it (the RAP key flattening, whose TRY could not have caught it either, and the RAP meta accessor), and the one remaining unguarded ASSIGN to an ANY TABLE symbol - loop-carried, in the RAP message walk - is guarded like its three siblings. A TIME_STMP component that is printable but not numeric keeps its (catchable) conversion inside a TRY instead of costing the box
* The app's keyboard shortcuts let go of the document when the component does. core/actions/Shortcuts installs ONE keydown listener on `document` and it is MODULE state, so it was the one addEventListener in app/webapp with no removeEventListener anywhere: the REGISTRY behind it is app-scoped and already cleared on an app switch and rebuilt by AppState.reset( ), but the listener itself outlived the component that installed it. On an FLP re-launch, where the page stays alive, it went on running the combo normalization plus a registry lookup on every keystroke of whatever came next, for the rest of the session, and could never be collected. Component.exit( ) calls Shortcuts.reset( ) now, next to the Server, Router, DevTools and cc/Dirty teardowns it already lists; the next app registering a shortcut installs a listener of its own, as on a fresh page

The two STATELESS ajson helpers the framework attaches to a serialization are one instance each per roll area instead of one per call: the no-empty-values filter (z2ui5_cl_ui5_util_json_fl) and the upper-case field mapping, which now lives next to it rather than in a private copy on z2ui5_cl_ui5_srv_model. Neither carries state - the filter has no attribute, the mapping an empty field table - and response_abap_to_json built BOTH on every single response. Lazily on first use, not in a class_constructor, which would have to be public or activation fails on a system while the transpiler stays green
* No statement of the framework tests sy-subrc to find out whether a dynamic ASSIGN succeeded any more, and none of them ASSERTs it. Both halves are release-dependent failures a green CI cannot see. A successful ASSIGN does not reset sy-subrc on every release (#1937, which is what put the IS ASSIGNED rule into z2ui5_cl_ui5_util_context=>unassign_data), so the test reads whatever an earlier statement left there - and inside a LOOP a failed ASSIGN additionally leaves the symbol on the PREVIOUS iteration's target, so a stale 0 does not skip an attribute, it renders that attribute's value under the next one's name. Thirteen sites were left, all found by the detector that ships with backlog/items/abaplint-subrc-after-assign.md: the exception-attribute and object renderers of the error dump and the message box (three loop-carried), the XCO user-exit lookup (where the wrong object was handed on and the caller reads the failure as "no user exit configured anywhere"), the request/response accessors of z2ui5_cl_ui5_util_http, the HTTP client pair, the row-delta write and the compression probe in z2ui5_cl_ui5_http_handler=>factory. The four ASSERTs are now raises or guards: ASSERTION_FAILED is a short dump no TRY can take, so on the two accessors every single request took - get_cdata, get_method and get_header_field all come through them - it bypassed the outer TRY of z2ui5_cl_ui5_http_handler=>main and answered with no body, no status code and none of the security headers, which is the exact state that TRY exists to prevent. The three table ASSIGNs of the message/data box that handed an unguarded field symbol on (msg_get_internal, data_get_headline) are guarded like their sibling data_render_tab already was
* The GET shell's ETag always describes the page it travels with. The tag was cached next to the BODY cache but reused off the BODY's key, and a 304 returns before that key is written - so after one 304 for config A the body cache still said B while the tag said A, the next GET of B matched the body key, reused A's tag and shipped `ETag: <A>` with body B. A browser that stores B under A's validator is then 304'd into keeping it once A is current, which is the stale shell the tag exists to prevent. The tag now carries the key it was computed for
* The start page escapes the class name it echoes in step 4. It is user input rendered with `v =` instead of `t =`, and the page bootstraps with complex binding syntax, so a `{` in it was read by UI5 as a binding path rather than shown - a malformed one takes the whole view build down. Reachable without a crafted class name: `class_editable` is a bound attribute, so a client can set it to abap_false in the same model delta that writes the name. It was the one `v =` in the shipped apps that carried neither a literal nor a binding
* The developer tools show the model and the bindings of a switch-mode app again. Their tab registry resolved the slot's model with a bare getModel( ), which with SWITCH_DEFAULT_MODEL_PATH is the app's OData client - it carries no getData( ), so both sub-views were hidden, while the bindings renderer next door resolved the framework model correctly and had plenty to show. It goes through ViewSlots.trackedModel now, like every other reader
* The developer tools' console capture no longer reports a value reachable twice as "[Circular]". It tracked everything seen in a flat set, so the SECOND of two sibling references - one lookup table two rows point at - was labelled circular although nothing loops. It follows the ancestor chain now, the way devtools/Format.js already did, and a real cycle (a self-referencing long array included) is still reported as one
* An edit made while a roundtrip that shipped NO delta was in flight stays pending too - the other half of the fix below. The value snapshot is written only when eB actually builds a model delta, so its ABSENCE says "this request carried nothing of this model"; clearing the whole set there dropped exactly the same edits one roundtrip earlier, and the model-free roundtrip is the COMMON one (a button press on a screen nothing has been typed into yet, a timer tick, a keyboard shortcut, a Back/Forward restore). A Switch flipped or a CheckBox ticked under the busy indicator was left out of the next delta and then reverted by the response's own model push
* A popup and a popover are torn down with the component. They are opened OUTSIDE its control tree (UI5 puts them in the static area), so nothing in the teardown reached them: on an FLP re-launch - which keeps the page alive - the dialog of the app that just ended stayed on screen over the one that replaced it, with every control inside it still alive and none of them having run its exit( ) - a Websocket kept its connection, a Timer kept ticking, and cc/Dirty kept window.onbeforeunload installed for unsaved changes of an app that no longer exists. Component.exit( ) routes both slots through ViewSlots.destroy( ), the same teardown an app switch and a MAIN rebuild use; the cc/Dirty module reset stays as the backstop
* An edit made while a roundtrip was in flight stays pending: the winning response cleared the sent model's whole changed-path set, so a field re-edited since its value went out, or edited for the first time meanwhile, was neither in the next delta nor re-applied over the response's model push - the backend's stale value overwrote what the user had typed. The value of every shipped path is snapshotted at dispatch and a path is cleared only while the model still holds it
