unreleased

! @abap2ui5/node-runtime: @abaplint/runtime 2.13.96, and accelerate() installs nothing any more. The runtime itself is linear on large tables now - LOOP ... WHERE over a sorted primary key binary-searches its block (abaplint/transpiler#1950) and CP compiles a pattern once (#1933) - and as fast as the fast paths accelerate() put on 2.13.93: the event roundtrip of 4000 rows takes 2.0 s, 2.5 s with the fast paths before, 28.4 s without. accelerate() and RUNTIME_VERSION stay exported, and the ./accelerate subpath with them, for the hosts that call it: it returns true on a runtime from 2.13.96 on, and false with one warning on an older one an overrides entry forces in. npm run unit:accelerated is gone with the fast paths
* Embedded mode: an embedded app no longer sets the host's page up as a mobile app. sap.m.App - the frontend's root - runs sap/ui/util/Mobile.init( ) when it is created, once per page with the settings of whoever calls first, and on a host page without a sap.m.App of its own that put height: 100% on <html>, a viewport meta tag that disables zooming and a format-detection meta tag on the host's page - and on an iPad took its scrolling (position: fixed on <html>) and hid the browser's UI. An embedded component makes that call first now, with everything off: a host that has made it already sees no change, a host without one keeps its page. What stays, on a phone or tablet, is the web-app-capable meta tag sap.m.App sets on every rendering (found by the review of abap2UI5/embed-control)
* Embedded mode: the custom controls of z2ui5_cci and the customer's own frontend artefacts of z2ui5_ccc load when the page reaches the system through a proxy that puts it under a path prefix of its own - the destination proxy of SAP Build Work Zone (https://<site>/dynamic_dest/<name>/sap/bc/z2ui5), an approuter route. The bundle (?z2ui5-bundle) handed the two BSP roots over as the system's absolute paths, which the page requested on its own origin, where nothing is - an embedded app naming a control of either BSP failed to load it. The z2ui5/embed module now also says which path the node has on the system (nodePath), and Component.init puts what the host's endpoint has in front of that path - the proxy's prefix, and the endpoint's origin when it is not the page's - in front of both roots. A proxy that rewrites the path leaves them as they are, and so does a page on the node's own origin
+ @abap2ui5/node-runtime: abap2ui5-transpile, a bin that is the README's "Your own apps" recipe in one command - npx abap2ui5-transpile abap apps: @abaplint/transpiler-cli at the version the package was built with (the installed one, or through npx; another version installed is refused with the install command that fixes it), open-abap-core fetched once at the commit the package records, the transpile config written, the transpile, and abap2ui5-own-apps over the output. --config runs a config of your own, --core an open-abap-core checkout of your own. Until now every host - mcp-server, cap2UI5, cap2UI5/samples - carried its own copy of those steps
+ @abap2ui5/node-runtime: TypeScript declarations for the entry point and the ./accelerate and ./compress subpaths (srv/*.d.ts, named by types on every export) - a TypeScript host, or an editor, sees the signatures of serve(), createApp(), createHandler(), initialize(), accelerate() and compress() without installing anything
! @abap2ui5/node-runtime: the package no longer carries the framework's own unit tests (output/*.testclasses.mjs, their generated runners output/index.mjs and _unit_open.mjs, downport/**/*.testclasses.abap) or the source maps of output/ - nothing a host loads or transpiles against was in them, and they were a third of the 21 MB every CAP project and every MCP user installed per release. The framework's suite runs in abap2UI5's own CI as before
+ Custom control z2ui5.cc.NativeBridgeScan: a scan button for apps running inside the abap2UI5 native mobile shell (abap2UI5/mobile-shell). It calls the shell's window.abap2ui5Native.scanBarcode( ), writes the result into value and fires OnScan; a cancelled or failed scan fires OnError with the bridge's message. Outside the shell it renders an invisible placeholder, so the same view runs unchanged in a browser (showInBrowser shows the button anyway, a press then fires OnError). Use it with the view builder: ns z2ui5, xmlns:z2ui5="z2ui5.cc"
+ Tables: copy to the clipboard with sap.m.plugins.CopyProvider (UI5 >= 1.110). Its mandatory extractData callback is now shipped as z2ui5/model/clipboard: core:require="{Clipboard: 'z2ui5/model/clipboard'}" and extractData="Clipboard.extractData" on the plugin, and each column says what it copies with the demo kit's CustomData - app:bindings (comma-separated paths, one clipboard cell each) and app:template (the text/html variant, optional). Until now the plugin threw on creation and took the view with it. Its copy button is your own Button wired with client->_event_client( cs_event-control_by_id ) to copySelectionData, which runs in the click and so keeps the browser's clipboard permission; Ctrl+C needs nothing
+ Claude Code plugin: this repository is a plugin marketplace now. /plugin marketplace add abap2UI5/abap2UI5, then /plugin install abap2ui5@abap2ui5, gives an agent the four skills (build-an-app with the app guide, view-chain-layout, abap-check, ui5-check) and the abap2UI5 MCP server (npx --yes -p @abap2ui5/mcp-server abap2ui5-mcp), plus four slash commands - /abap2ui5:new-app (an app from a plain-language description: sample catalogue first, one class and its .clas.xml, validated and screenshotted, finished with the gates), /abap2ui5:check (abaplint and the abap2UI5 linter over the changed classes, findings explained, the mechanical ones fixed), /abap2ui5:find-sample (the best three matches across the three sample catalogues) and /abap2ui5:explain (lifecycle, events, bindings and view tree of an app class) - and a read-only abap2ui5-reviewer subagent that reports findings against the four skills as file:line. Each command works with the MCP server and without it. The plugin is plugin/, its skills generated from .claude/skills (npm run plugin, gated by check:plugin); the framework itself is unchanged


2026-09-29 v1.146.0
-------------------
* Embedded mode: the developer tools of an embedded app no longer capture the host page's console and errors. Their capture wraps the page's console and listens to its window, and on a host's page that was the host's output - a host's console.error or uncaught error (with whatever secret it carried) landed in the app's Log tab and bug report, and with "open on error" opened the app's tools. Embedded, the Log tab has the framework's own error log and the backend messages
* Embedded mode: Restart in the error dialog - and Refresh in the fallback overlay, Restart in the developer tools - restarts the app in place instead of reloading the page. On a host's page the reload took the host app, and everything the user had there, with it. The failed app ends, and the app the component was created for starts again in a new session; a page of the app's own reloads as before
* Embedded mode: the frontend leaves no z2ui5 global on the host page. UI5 1.x exports every class it creates as a global, so window.z2ui5.Component, z2ui5.controller.App/View1, z2ui5.devtools.DeveloperTools and a z2ui5.cc.* per custom control appeared on every page - also after abap2UI5 had dropped its own global. On a page an embedded component runs on they are taken off again, and a z2ui5 object of the host's own keeps exactly what it held. A page of the app's own keeps them: UI5 1.71 looks a base class up by that name when something extends one of ours
* Embedded mode: a starting app no longer takes the focus from the host page. sap.m.App focused the first input of the app's first page (on UI5 1.136 every app did, hello world included), and SET_FOCUS, a CONTROL_BY_ID focus( ) and the Focus control moved it as well - also out of a host field the user was typing in. An embedded app now moves the focus only while it is in the app, or while it is nowhere and the user's last focus or click went into the app; S_FOCUS no longer reports a control of the host
* @abap2ui5/node-runtime: "Your own apps" works for a class that extends something - an exception class of the app's own, say. The README's transpile config wrote no imports, so such a class did not load; with them (addCommonJS) the class imported what it extends from the transpile's output/, which holds a second copy of every library object, and that second CX_ROOT replaced the package's - from then on every request failed. The new bin abap2ui5-own-apps keeps your classes out of the output and points their imports at the package's; the README's recipe runs it
+ @abap2ui5/node-runtime: createApp() - and so serve() and the dev server - gzips the responses, as the ICF does on an SAP system when the framework asks it to: the page shrinks from about 360 KB to 85 KB, a roundtrip's JSON by two thirds. The compressed page goes out under the ETag "<tag>-gzip", which the framework revalidates to a 304 like the plain one. compress() is exported for an express app of your own - mounted in front of createApp(), which has one, it compresses once and tags once; createApp({ compression: false }) leaves it out
+ @abap2ui5/node-runtime: a roundtrip with a large table is linear again. Two functions of @abaplint/runtime made it quadratic - LOOP ... WHERE over a sorted primary key scanned every row (once per node in the JSON serializer), and CP walked the whole rest of a string behind a trailing * (once per token in the XML parser that reads the draft) - so the event roundtrip of 2000 table rows took 22.6 s in a CAP project, 1.8 s now. initialize() installs fast paths for both that answer exactly what the originals answer, validated for the one runtime version the package pins; a host that boots through output/init.mjs itself calls accelerate() from "@abap2ui5/node-runtime/accelerate"
* @abap2ui5/node-runtime: the test apps of abap2UI5's own browser tests (ZCL_TST_*) are no longer in the package. 1.145.0 shipped ten of them in output/ and downport/ and loaded them at boot, so every host - a CAP project with @cap2ui5/cds-plugin in production included - started them on ?app_start=ZCL_TST_HOST. The pack now fails when one is left anywhere in the tarball
* @abap2ui5/node-runtime: express 4 (from 4.21) works next to express 5. The peer range named express 5 only, so npm nested a second express in every project on express 4 (a CAP project, for one), and createApp() used express 5's "/{*path}" route syntax, which matches no request under express 4. createApp() mounts the handler with app.use() now, and serve() rejects on a port that is taken instead of resolving
+ @abap2ui5/node-runtime: package.json records the open-abap-core commit output/ was built against (abap2ui5.openAbapCore), and the README's "Your own apps" checks out that commit instead of cloning whatever HEAD is that day
+ Embedded mode: a component that runs inside a page of its own - loaded through ?z2ui5-bundle (z2ui5.embed.Container of abap2UI5/embed-control), or given componentData.embedded = true by a host's ComponentContainer - leaves the URL to its host: it neither listens to nor writes the hash, and no request sends it. Before, every roundtrip ended with a replaceHash("") that took a Fiori elements object page's route away and sent the host back to its list, and a host route reading like #/app/<CLASS> started that class instead of the app the host asked for. The z2ui5/embed module of the bundle passes the flag; the page, the BSP and the launchpad run as before
+ Page transitions: view_display( transition = ... ) animates the new main view (slide, baseSlide, fade, flip, show); nav_app_leave( ), the browser Back button under hash routing and transition_back = abap_true play it reversed. Try them all with the sample Z2UI5_CL_SMP_APP_531 of abap2UI5/samples
+ @abap2ui5/bsp on npm: a UI5 app as an abapGit BSP and back. `npx @abap2ui5/bsp app2bsp webapp --name ZMYAPP` writes the BSP with its ICF nodes into a folder to push to git and pull with abapGit, `bsp2app` turns a serialized BSP into an app folder again, `check` holds the page rules - and refuses up front what the system would break (a hyphen in a file name, a line over 255 characters, a binary file). The BSP Z2UI5 of abap2UI5/frontend is written with the same code, byte for byte as before
! Default CSP: script-src carries 'wasm-unsafe-eval', so a page may compile WebAssembly - the camera scanner of SAPUI5 (sap.ndc.BarcodeScannerButton) and the BarcodeScanner of abap2UI5-addons/custom-controls decode with ZXing-C++ compiled to WebAssembly and failed with a CompileError before. 'unsafe-eval' stays out: no string becomes code. An exit that writes its own policy keeps the keyword for them
