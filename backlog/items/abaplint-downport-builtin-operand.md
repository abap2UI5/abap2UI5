# Downport: hoist a built-in function out of the generated `WITH KEY` operand

## What happens

Source, valid at v750:

```abap
IF NOT line_exists( mt_names[ table_line = to_upper( is_node-name ) ] ).
  RETURN.
ENDIF.
```

`abaplint --fix` with the downport rule at v702 produces:

```abap
READ TABLE mt_names WITH KEY table_line = to_upper( is_node-name ) TRANSPORTING NO FIELDS.
temp53 = sy-subrc.
IF NOT temp53 = 0.
  RETURN.
ENDIF.
```

The rewrite of `line_exists( )` and of the table expression is correct. What is
not is that the key operand was carried over verbatim. `to_upper( )` is one of
the built-in functions release 7.02 introduced, and a built-in function is only
recognised as one in an operand position that admits a string expression. The
`WITH KEY comp = …` operand does not become a general expression position until
7.40, so a 7.02/7.31 compiler falls back to the only other reading of
`name( … )` available to it — a functional method call — and reports

```
Die Methode "TO_UPPER" ist unbekannt bzw. PROTECTED oder PRIVATE.
```

as a `SYNTAX_ERROR` of the whole class pool. In abap2UI5#2664 that class is the
framework's client, so every abap2UI5 application on the system was down.

The same statement is already generating temporaries — `temp53` for the
`sy-subrc` — so the machinery to hoist is there; it just is not applied to the
operand.

## Expected

```abap
DATA temp54 TYPE string.
temp54 = to_upper( is_node-name ).
READ TABLE mt_names WITH KEY table_line = temp54 TRANSPORTING NO FIELDS.
```

A plain assignment *is* an expression position at 7.02, so one temporary is the
entire fix.

## Scope — where the hoist is needed, and where it must not happen

Needed wherever the downport emits an operand into a position that is not a
general expression position before 7.40:

- `READ TABLE … WITH [TABLE] KEY comp = <operand>` — generated by the table
  expression, `line_exists( )` and `line_index( )` rewrites
- `DELETE … WITH TABLE KEY comp = <operand>`
- the `WHERE` condition of an internal-table statement, when the rewrite puts
  an operand there

It must **not** fire on:

- a **functional method call** (`client->get_event_arg( 1 )`) in the same
  positions. Those parse as method calls at 7.02 and are accepted — that
  reading is precisely what makes the built-in fail. Hoisting them too would be
  harmless but would churn code that works; hoisting them is not what this asks
  for.
- `lines( )`, `strlen( )`, `numofchar( )` and the other pre-7.02 built-ins. The
  same downported method contains `READ TABLE lt_parts INTO temp51 INDEX
  lines( lt_parts )` ten lines above the failure and the 7.31 compiler had no
  complaint about it; the dump named the `to_upper( )` line and nothing else.
- anything at a target of 7.40 or higher, where the position is an expression
  position and the operand is legal as written.

## Why the linter cannot catch it as a rule instead

There is nothing wrong with the input. It is valid v750 ABAP, and the config
that lints the downported branch (`ABAP_702.yaml` in abap2UI5) passed it as
well — abaplint does not model which operand positions accept a built-in
function at which release. The defect is introduced by the downport, which
makes the downport the place to repair it.

**Where the detector is an approximation of the rule:**

- The detector IS the gate: both import `.github/scripts/lib/downport-operands.mjs`, so a site here is a line `npm run check:downport` would fail on, and the two cannot drift apart.
- Sites by repository: none. abap2UI5 itself is expected to be at zero - the one site it had is the defect this item was written from, and it was repaired in the same change that added the gate.
- The positions are recognised line by line rather than statement by statement. A key or a WHERE operand split across lines still carries its `= builtin( ` on one of them, so the count holds; a construct built by a macro is not followed.
- The negatives are approximated by "a call that is not one of the 39 built-ins": a constructor expression or a control-flow keyword in the same position is filtered out by name, but the set is hand-written, so read the count as an order of magnitude rather than an exact figure.
- abaplint knows all of this properly - it models the release levels and it owns the downport rewrite that introduces the construct. The right fix is in the downport itself (hoist the call into a variable, which IS an expression position at 7.02), not in a source-shape rule; this probe measures how often the rewrite would have to do it.
